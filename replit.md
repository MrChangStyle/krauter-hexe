# Little Farming (Kräuterhexe)

**Little Farming** is the app; the **Kräuterhexe** (plant/mushroom/insect scanning, archive, care tasks) is its first module, "Meine Farm" (animals) comes next — see `docs/meine-farm-app.md`. User-facing text names the app "Little Farming" (manifest, page title, header, login, push default title, PDF footers and file names `LittleFarming_*.pdf`) and the module "Kräuterhexe" (scan page badge, login subtitle). "Kräuter-Hexe" is also the name of the AI herb advisor under Werkzeug and stays. Package names, DB, Cloudinary folder and the Render service keep their old names on purpose.


Eine mobile-first, deutschsprachige Web-App, mit der Nutzer wilde Pflanzen per Foto scannen, per KI bestimmen lassen und in einem kategorisierten Archiv (Giftige Pflanzen, Essbare Pflanzen, Heilkräuter, Giftige Pilze, Essbare Pilze, Bäume, Sträucher, Moose) sammeln können.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server
- `pnpm --filter @workspace/pflanzenscanner run dev` — run the frontend
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/api-server run migrate:images` — one-off: move photos still stored in Replit Object Storage over to Cloudinary (must run on Replit; `--download-only` just backs them up locally)
- Required env: `DATABASE_URL` — Postgres connection string
- Required secret: `GEMINI_API_KEY` — user-provided Gemini API key (direct Generative Language API, not the Replit AI Integrations proxy)
- Required secret: `JWT_SECRET` — signing key for the login cookie (≥16 characters, any long random string). Changing it logs everyone out.
- Required secret: `CLOUDINARY_URL` — `cloudinary://<api_key>:<api_secret>@<cloud_name>` from the Cloudinary dashboard; all scan photos are uploaded there
- Required secret: `CRON_SECRET` — Bearer token for the cron endpoint (see "Push-Benachrichtigungen (Cron)" below)
- Optional secret: `REGISTRATION_CODE` — when set, `POST /auth/register` additionally requires this invitation code, and "Mit Google anmelden" only works for addresses that already have an account
- Optional secrets: `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — OAuth client (type "Webanwendung") from the Google Cloud console. Only when **both** are set does the login screen offer "Mit Google anmelden". Registered redirect URI: `<origin>/api/auth/google/callback`
- Optional env: `PUBLIC_BASE_URL` — canonical public origin (e.g. `https://kraeuter-hexe.onrender.com`). Used to build the Google callback URL instead of trusting proxy headers; set it wherever Google sign-in is used
- Optional env: `CLOUDINARY_FOLDER` — folder for uploads (default `kraeuterhexe`)
- Optional env: `OPEN_REGISTRATION` — `true` = new accounts are approved at once (public app); unset = family mode (new accounts wait for the owner)
- Optional env: `SCAN_DAILY_BUDGET` — max AI scans per Berlin day for the whole app (owner excluded); unset = no app-wide cap. render.yaml sets 300
- Optional env: `REGISTRATION_DAILY_CAP` — max new accounts per rolling 24 h while `OPEN_REGISTRATION=true` (default 50)
- Optional secrets: `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` — Cloudflare Turnstile on the registration form; only when **both** are set is a token required
- Optional env: `LEGACY_ORIGINS` — comma-separated old addresses the canonical address accepts device data from in the move helper (render.yaml: `https://kraeuter-hexe.onrender.com`)
- Optional env: `SITE_PASSWORD` — Vorschau-Schutz: while set, the whole site shows only a password page until it is typed once per device (docs/landingpage.md). Delete it to go public.
- Optional env: `TRUST_PROXY_HOPS` — proxies in front of the server whose X-Forwarded-For is trusted for `req.ip` (default 1 = Render's proxy)

## Push-Benachrichtigungen (Cron)

Push-Erinnerungen werden nicht mehr durch einen `setInterval` im Server-Prozess ausgelöst, sondern durch einen externen Cron-Dienst. Das ist nötig damit Erinnerungen auch nach einem Scale-to-Zero (Autoscale mit 0 Mindest-Instanzen) zuverlässig ankommen.

**Einrichtung (einmalig, nach dem Deployment):**

1. Öffne [cron-job.org](https://cron-job.org) (kostenlos) und lege einen neuen Cronjob an.
2. **URL:** `https://<deine-deployed-domain>/api/cron/trigger-notifications`
3. **Methode:** `POST`
4. **Header:** `Authorization: Bearer <CRON_SECRET>`
5. **Intervall:** jede Minute (damit keine Erinnerungsminute übersprungen wird)
6. Den Wert von `CRON_SECRET` findest du in den Replit Secrets dieses Projekts.

**Lokal testen:**
```bash
curl -X POST https://<deine-deployed-domain>/api/cron/trigger-notifications \
  -H "Authorization: Bearer <CRON_SECRET>"
# → {"triggered": 0}   (0 wenn gerade kein Reminder fällig ist)
```

Die Funktion ist idempotent: mehrere Aufrufe innerhalb derselben Minute senden maximal eine Benachrichtigung pro Aufgabe/Guide pro Tag.

Derselbe Cron schickt ab 07:30 (Berlin) einmal täglich je Farm den Garten-Push des Beet-Architekten (Termine, die heute beginnen, und Frostwarnung für die kommende Nacht).

## Architecture decisions

- **Direct Gemini API key instead of Replit AI Integrations.** Both the managed OpenAI and Anthropic integrations were blocked by an account-upgrade requirement, and the user declined to upgrade or provide their own OpenAI/Anthropic key. The user instead provided their own `GEMINI_API_KEY` (via the secure secrets flow), so the backend calls the Gemini Generative Language API directly with `@google/genai` rather than going through the Replit AI proxy. Revisit if a managed integration becomes available.
- **Model choice is driven by IMAGE-request reliability, not text.** This app sends photos, and multimodal availability differs sharply from text on this key: `gemini-3.5-flash` and `gemini-flash-latest` answer text fine but return 503 "high demand" for nearly every image request, while `gemini-flash-lite-latest` reliably handles image requests (verified 4/4). So the primary model is `gemini-flash-lite-latest`, with `gemini-flash-latest` as fallback, and transient 503/429s are retried with backoff (see `requestPlantJson` in `plantIdentification.ts`). Always validate a model against a real image request, not a text smoke test. Older versioned IDs (`gemini-2.5-flash`/`gemini-2.0-flash`/`gemini-2.5-flash-lite`) return 404 "no longer available".
- **`thinkingConfig.thinkingBudget: 0` is required.** Without it, Gemini flash models silently consume part of `maxOutputTokens` on internal "thinking" tokens, truncating the JSON response before it's complete — this looked like a generic "invalid JSON" parse failure, not a token-budget issue. JSON is also parsed defensively (fences stripped, outermost `{...}` extracted) in case the model wraps or pads the output.
- **Category/status fields use native Postgres enums**, not free text, so invalid values can never be persisted regardless of code path — critical since these drive the safety badges.
- **Deterministic category override**: if the model says a plant is poisonous for humans, the archive `category` is forced to `poisonous` (unless the model picked a form-based bucket — `mushroom`, `tree`, `shrub`, `moss` — those always keep their own category; safety stays visible via the status badges), rather than trusting the model's own category pick — keeps archive grouping safety-consistent even if the model's `category` and `humanStatus` fields disagree.
- **Safety-first fallback**: any missing/unparseable `humanStatus` or `poultryStatus` defaults to `poisonous`, never to a "safe" value.
- **Duplicate scans are de-duplicated by botanical name.** `POST /plants/scan` matches the identified botanical (Latin) name case-insensitively against the archive; on a match it returns the existing entry with `alreadyInArchive: true` and creates no new row. The scan UI then points the user to the existing entry instead of navigating to a freshly created one.
- **Deleting an archived plant is password-gated server-side.** `DELETE /plants/:id` requires a `password` in the request body, verified against the `DELETE_PASSWORD` env var (stored as a Replit Secret, never hardcoded). It fails closed: if `DELETE_PASSWORD` is unset the endpoint returns 503 and deletes nothing. The password travels in the request body (not the URL/query) so it is never written to request logs.
- **Plant photos are served as binary images, never embedded in JSON.** All JSON responses (list, detail, scan result) exclude `image_data`; photos come from `GET /plants/:id/image`, which decodes the stored data URL and serves real image bytes with `ETag` + `Cache-Control: public, max-age=86400` (304 revalidation) and `X-Content-Type-Options: nosniff` behind an image-MIME allowlist (unknown stored MIME → `application/octet-stream`, so a hostile stored payload can never run as same-origin HTML; scan ingestion also rejects non-image data URLs). **Why:** embedding base64 photos made list payloads scale with total image bytes — production once reached ~69 MB for 13 plants, which mobile browsers simply cannot load. As a bonus the browser now caches photos independently of data. The category summary counts in SQL (`count(*) … group by`) instead of loading full rows.
- **Pilze are shown split into "Giftige Pilze" / "Essbare Pilze" — view categories, not data categories.** The DB/API keep the single `mushroom` category; the UI derives the two sub-groups from the required `humanStatus` enum. `src/lib/view-categories.ts` is the single source of truth for view-category order, labels, and mapping, used by both the Kategorien page and the PDF export. The summary endpoint returns per-humanStatus counts (`poisonousCount`/`edibleCount`) so the overview still needs no row loads. **Why a derived split:** zero migration — it applies automatically to already-scanned mushrooms, including those in the separate (workspace-read-only) production database; both mushroom views share one cached `category=mushroom` list query and are narrowed client-side.
- **Mushroom edibility requires a verified two-photo scan.** The scan page has a dedicated "Pilz scannen (2 Fotos)" flow: Bild 1 von oben (persisted as an IndexedDB draft — `mushroomDraft` store, DB v2 — so the camera-reload on low-memory phones can't lose it), then Bild 2 von der Seite; both photos are enqueued as ONE queue item, sent to Gemini as one labeled request, and stored on the entry (`image_data_side`, served via `GET /plants/:id/image/side`, shown on the detail page; `hasSideImage` in every plant response). A mushroom is listed as "essbar" ONLY when the side view exists AND the model set `mushroomEdibleConfident=true` (zweifelsfreie Art, eindeutig essbar, keine Verwechslungsgefahr mit giftigen Doppelgängern; missing flag = false). Enforcement is layered: `identifyPlant` downgrades to `poisonous` + German warning prefix in `edibilityDetails` at write time, and the shared `plantSelection` applies the same rule as a SQL CASE at read time (also in the category-summary counts) — so legacy single-photo mushrooms and maintenance PATCHes can never surface an unverified "essbarer Pilz". Stored rows are deliberately not mutated by the read gate; rescanning such an entry with the Pilz-Scan upgrades it in place via the botanical-name dedup (only when the existing row lacks a side image — a later 1-photo scan can never downgrade a verified entry).
- **Password-gated maintenance endpoint `PATCH /plants/:id`** (body: `password` + optional `imageData`/`habitat`/`siteConditions`/`otherUses`/`fertilizerTips`/`category`; strict field allowlist; `imageData` must be a JPEG/PNG/WebP data URL). **Why it exists:** the production deployment has its **own separate database** that is read-only from the workspace, so recompressing photos or backfilling new fact-sheet fields on already-scanned production plants can only happen through the deployed app itself. Both delete and patch verify the password by comparing sha256 digests with `timingSafeEqual` (constant-time).
- **Persist-first scan queue.** Every captured photo — online or offline — is stored locally in **IndexedDB** first (not localStorage, since photos are large data URLs) and then scanned from the queue; when online the drain starts immediately. **Why persist-first:** low-memory phones reload the tab seconds after the camera closes, killing an in-flight direct scan request and losing the photo — with the queue the photo survives the reload, is rescanned automatically on the next load, and the scan page still shows the result preview (server-side botanical-name dedup keeps crash-rescans duplicate-free). The drain reports each outcome as a `ScanResult` carrying the queue item id, so the scan page matches results to the exact photo it is waiting on (older backlog results can't mask the current photo's failure); a single new plant navigates to its detail page, several results render as a batch preview list. The queue lives in a React context (`src/lib/scan-queue-context.tsx`) over a thin IndexedDB wrapper (`src/lib/scan-queue.ts`); the "Warteschlange" page (`src/pages/pending.tsx`) lists waiting/failed items with retry/remove. Invariants that keep it safe: (1) **the transient "scanning" state is never persisted** — only `pending`/`error` are written, so a tab closed mid-scan leaves the item `pending` and it is retried on next load (nothing gets stuck); any legacy persisted `scanning` is normalized to `pending` on read, and the queue page re-reads storage on mount. (2) The drain is **single-flight** (a synchronous `processingRef` lock) and re-reads storage each iteration, so overlapping triggers can't double-process and a removed item can't be resurrected (the error-write is an atomic get+put in one IndexedDB transaction). (3) Network vs. server failures are told apart by `isNetworkError` (duck-typing the generated client's `err.name`): a network drop reverts the item to `pending` and stops the drain; a server error marks it `error` for manual retry.
- **Background sync is foreground-only (accepted limitation).** Draining happens only while the app is open: on the `online` event, on load when online, via a 30s safety-net interval, and via the manual "Jetzt scannen" button. True OS-level Background Sync is deliberately not implemented (unreliable, and unsupported on iOS), so queued photos scan when the user next opens the app with a connection — not while it is fully closed. Offline *capture* itself also depends on the installed PWA's cached app shell, which exists in production but not on the dev server (so a fully-offline relaunch can only be verified on the deployed PWA).
- **Sign-in is platform-independent: email + password, scrypt hashes, JWT cookie.** The app previously used Replit Auth (OIDC), which is bound to the Replit account that owns the repl and cannot follow the app to another host. It is replaced by `POST /auth/register` / `POST /auth/login` against the existing `users` table (`password_hash` column added; ids, `approved` and leaf counts untouched, so every existing account and all its data survive). Passwords are hashed with node's built-in **scrypt** (`src/lib/password.ts`, format `scrypt$N$r$p$salt$hash`, constant-time compare) — no native dependency to build on the new host. The session is a **JWT** (HS256, `jose`, 30-day TTL, `src/lib/token.ts`) in an HttpOnly/SameSite=Lax cookie named `auth`, re-issued at most once a day so long-lived logins roll forward. **Why no session table:** the middleware re-reads the user row on every request, so revoking approval or deleting an account takes effect immediately even though the token itself is stateless; the legacy `sessions` table is kept but unused. Registering with an email that already exists but has **no** password *claims* that row — that is how the pre-existing family accounts set their first password. That path inherits the row's `approved`/`isOwner` flags, so it is **refused unless `REGISTRATION_CODE` is set**: without it, guessing a family member's address would be enough to take over their (or the owner's) account. Registering a brand-new address without a code stays allowed — such an account starts unapproved and can do nothing until the owner lets it in. Login failures are rate-limited in memory (10 per 15 min per IP+email) and always answer with the same generic German message, so the endpoint reveals nothing about which emails exist.
- **Public registration is a switch, with brakes that do not need the owner.** `OPEN_REGISTRATION=true` makes new accounts (password and Google) `approved` at creation; everything else about the account model stays (owner = first account, legacy password-less rows still need `REGISTRATION_CODE` to be claimed, `approved=false` still locks an account out). **Why brakes:** every scan is paid from the owner's Gemini key and the per-user limit (15/day) is worthless once anyone can make more accounts. So: (1) `SCAN_DAILY_BUDGET` caps AI scans app-wide per Berlin day inside the same transaction as the per-user count — a second advisory lock, always taken *after* the per-user one so two transactions cannot deadlock; a refused scan answers 429 `SCAN_BUDGET_REACHED`, which the queue treats like the user limit (item stays pending, retried after midnight) with its own toast. (2) New accounts are limited per client address (5/hour, in memory) and per app (`REGISTRATION_DAILY_CAP`, counted in the DB, so a restart cannot reset it) — `lib/registrationPolicy.ts`. (3) Optional Cloudflare Turnstile on the registration form (`lib/turnstile.ts`, fails closed; the site key reaches the client through `GET /auth/providers`, so no rebuild is needed to switch it). Google sign-up skips Turnstile (Google is the bot check) but has the same address/day limits. **`trust proxy` is set** (`TRUST_PROXY_HOPS`, default 1): before, `req.ip` was Render's proxy, which made the per-address limits shared by everybody.
- **Deleting an account goes through one function: `deleteAccount(userId)`** (`api-server/src/lib/accountDeletion.ts`). The user-id columns are plain text without foreign keys, so deleting only the `users` row — what the owner's "Entfernen" used to do — left favourites, tasks, care guides, push subscriptions and scan history behind. The function deletes those rows, sets `scanned_by_user_id` to NULL on plants/insects (the shared archive stays; the Nutzungsbedingungen grant its photos to the archive), then deletes the user — all in one transaction. "Meine Scans" photos live only on the device, so nothing on Cloudinary belongs to one account alone. Used by both `DELETE /auth/user` (self-service under Home → "Dein Konto"; confirmed with the password, or for Google-only accounts by typing the email; wrong attempts share the login lock-out) and the owner's `DELETE /users/:id`. The owner account can never be deleted (nobody else could approve or moderate, and the next registration would silently become owner). **Rule:** every new table with a user id is added to `deleteAccount` in the same PR — `accountDeletion.test.ts` reads the real schema and fails for any `user_id`/`scanned_by_user_id` column the function does not handle. Rows orphaned by earlier owner deletions are removed only on the owner's explicit request: Home → Benutzerverwaltung → "Datenreste früherer Konten" (`GET /users/orphaned-data` counts and changes nothing; `POST /users/orphaned-data/cleanup` with `{confirm: true}` deletes/unlinks in one transaction, `lib/orphanCleanup.ts`). It walks the same `PERSONAL_TABLES` / `ARCHIVE_TABLES` lists as `deleteAccount`, so the two can never disagree. `orphanCleanup.integration.test.ts` runs both against a real Postgres when `TEST_DATABASE_URL` equals `DATABASE_URL` (a throwaway DB with the schema pushed — the test truncates tables); it is skipped in CI.
- **Moderation: report → owner decides per content** (`api-server/src/lib/moderation.ts`, `routes/reports.ts`, table `reports`). Public content is the shared photo of a plant/insect and usernames in the leaderboard; every approved account can report it (one open report per account and content via a partial unique index, max 20 per account and 24 h, own name not reportable, the reporter stays anonymous to the reported person). The owner sees open reports grouped per content on Home → "Meldungen" and acts once for the whole group: dismiss, remove photo (clears `image_url`/`image_url_side`/`image_data*`/quality and unlocks; **`has_side_image` stays**, because the mushroom edibility rule depends on the two-photo verification; Cloudinary files are deleted only after the transaction commits), reset username, or block the account (`approved=false`, `blocked_at` set, name removed; the owner can never be blocked). `blocked_at` lets the app say "Konto gesperrt" instead of "Warte auf Freigabe"; approving the account again in the user management clears it. Usernames pass a short blocklist (`lib/usernameFilter.ts`, substring match, deliberately conservative — moderation handles the rest). The table is created by `schemaUpgrade.ts` (CREATE TYPE in `DO … duplicate_object` blocks) and was checked to produce the same structure as the Drizzle schema. `deleteAccount` removes the reports a person filed and the reports about their name. `moderation.integration.test.ts` covers all of it against a real Postgres (run the integration files with `--no-file-parallelism`; they share the database).
- **Moving to a new domain carries device-only data along** (`src/lib/move.ts`, `src/lib/move-channel.ts`, `src/components/move-screen.tsx`, `src/pages/umzug.tsx`, `GET /api/app-config`). IndexedDB and localStorage belong to one origin, so the scan queue, an unfinished mushroom scan, the local image store (photos behind "Meine Scans" and `local_image_id` rows) and the `lf-my-photos-v1` mapping would stay behind at the old address. **The switch is PUBLIC_BASE_URL:** `/api/app-config` returns its origin as `canonicalOrigin`; any other origin (never localhost) shows the move screen instead of the app — but only once the config is known, so offline use is unaffected. The move screen opens `<canonical>/umzug` in a new window; that page says "ready" to its opener, the old page sends batches (queue/draft/local first, then images 10 at a time) and waits for each acknowledgement; messages go only to the exact canonical origin and are accepted only from `LEGACY_ORIGINS`. Unpacking validates everything (only `data:image/` URLs, known queue statuses/kinds, whitelisted localStorage keys — never the cached auth user) and never overwrites what the new address already has. Fallback for devices where windows cannot talk (iOS home-screen apps have their own storage): "Als Datei sichern" downloads a JSON file that `/umzug` imports. Nothing is deleted at the old address; after a successful move it sets `lf-moved-to`, unsubscribes push (the new address subscribes again) and from then on redirects to the same path at the new address. A device with nothing to move is redirected at once. The flag is read once when the screen opens — re-reading it after the move skipped the success message (caught by the browser test).
- **"Meine Farm" data is private per farm** (`lib/db/src/schema/farm.ts`, `middlewares/requireFarm.ts`, `routes/farms.ts`). Tables: `farms`, `farm_memberships` (role `admin`/`caretaker`/`guest`), `herds`, `farm_animals` (registration number unique per farm, `archived_at` instead of deleting), `medical_records`, `weight_logs`, `food_logs`, `cameras`, `camera_events`; every child table has `farm_id` with `ON DELETE CASCADE` to `farms`. Every farm route has `:farmId` and goes through `requireFarm(minRole)`: approved account + membership of exactly that farm, else **404** (a stranger cannot tell the farm exists), role too low → 403. The app owner has **no** automatic access. Handlers must filter every query by `req.farm.farmId`. Species include the animal keys of the plant module (`poultry`, `rabbit`, `guineaPig`, `cat`, `horse`) so plant toxicity can later be matched to farm animals. DDL is in `api-server/src/lib/farmSchemaStatements.ts`, **generated** with `drizzle-kit export --sql` and made idempotent — regenerate after changing `farm.ts`; checked to produce the same structure as `drizzle-kit push`, and a second start is a no-op. Account deletion: a farm whose last member leaves is deleted with all its animals; a farm losing its only admin gets the longest-standing member as admin. The one-time cleanup applies the same rules to leftovers of old deletions. `farm.integration.test.ts` covers isolation, cascades and handover against a real Postgres.
- **Farms and members** (`api-server/src/lib/farmMembers.ts`, page `src/pages/farm.tsx`, nav item "Farm"). First visit calls `POST /farms/ensure-own`: an account without any membership gets a farm "Meine Farm" as admin (per-account advisory lock, so two tabs cannot create two); an account already invited to a farm gets none and can add one via "Weitere Farm" (max 5 as admin). Admins add members by the email of an existing, approved, not blocked account (max 30 per day per admin, which also slows probing which emails exist), change roles and remove members; anyone can leave. Invariants, enforced under a per-farm lock: a farm always keeps an admin, and its last member cannot leave — the farm is deleted instead, with its exact name typed as confirmation (cascades to all animals). Emails of members are shown to admins only. The chosen farm is a per-device display choice (`lf-active-farm` in localStorage); every request names its farm.
- **Animals and herds** (`api-server/src/lib/farmAnimals.ts`, `routes/farm-animals.ts`, `src/components/farm-animals-section.tsx`, `src/pages/farm-animal.tsx`, route `/farm/:farmId/tier/:animalId`, `neu` = new). Reading needs `guest`, writing `caretaker`. An animal needs photo, name, species, sex, birth date (real date, 1950 – today) and ring/ear tag number; the number is unique per farm (409 otherwise). A herd is only accepted from the same farm (checked in the handler, and the read join also matches `farm_id`), so no id from another farm leaks or can be attached. Animals are **archived, never deleted** (`POST …/archive`), so their health records stay; deleting a herd keeps its animals (herd set to null). Photos: `PUT …/photo` takes a downscaled JPEG/PNG/WebP data URL (max 8 MB), stores it in Cloudinary and removes the old one; on create the animal is saved first and a failed photo upload only shows a hint. Deleting a farm (also through account deletion or the cleanup) removes its animal photos from Cloudinary after the commit. `farmAnimals.integration.test.ts` covers isolation, roles, uniqueness, validation, archive and herd deletion against a real Postgres.
- **Health, weight, stall tasks, export** (`api-server/src/lib/farmHealth.ts`, `lib/farmTasks.ts`, `routes/farm-health.ts`, `routes/farm-tasks.ts`; app: `components/farm-animal-health.tsx`, `components/farm-tasks-section.tsx`, `components/farm-export-card.tsx`, `lib/farm-health.ts`, `lib/farm-export-pdf.ts`). The operator's name/address/email live in `src/lib/legal.ts` and are deliberately `[bitte ergänzen]` until the owner provides them — the pages show a visible "Entwurf" notice meanwhile instead of invented data.
- **"Mit Google anmelden" is an optional second door, not a dependency.** `GET /api/auth/google` → Google → `GET /api/auth/google/callback` (authorization code flow with PKCE, `src/routes/google-auth.ts`). It ends in exactly the same `auth` cookie as a password login, so nothing downstream knows the difference, and with `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` unset the routes are inert and the button is hidden (`GET /api/auth/providers`). An account is only matched or created from an address Google reports as **verified**; existing rows keep their `approved`/`isOwner` flags and only get missing name/photo filled in. When `REGISTRATION_CODE` is set an unknown address is turned away rather than creating a row — a redirect has nowhere to type the invitation code. The in-flight state lives in a signed, HttpOnly `__Host-` cookie (HMAC with `JWT_SECRET`): an unsigned one could be planted by an attacker to make somebody finish the sign-in as *their* Google account. Everything that can go wrong returns to the app as `?anmeldung=<code>`, which the login screen turns into German text.
- **Photos live on Cloudinary, not in the database or a Replit bucket.** Scan photos are uploaded to Cloudinary (`src/lib/imageStorage.ts`) and only the resulting public `https://res.cloudinary.com/...` URL is stored in `image_url` / `image_url_side`. **Why:** Replit Object Storage authenticates through a sidecar on localhost, so it silently stops working off-platform, and storing base64 in Postgres was what made list payloads explode in the first place. Uploads are **non-fatal**: a failing or unconfigured Cloudinary leaves the scan intact (the photo still lives in the device's IndexedDB and is retried by the image-backup endpoint). The SDK is imported lazily and the credential is parsed by us first (a pasted `CLOUDINARY_URL=cloudinary://…` line is tolerated) — otherwise a mistyped credential would crash the whole server at boot, because the SDK validates the env var at import time. Rows still holding a legacy `/objects/...` path are ignored by the client and converted by `migrate:images`. `GET /plants/:id/image` (and the insect/side variants) stay in place but now **302-redirect** to the CDN when the row has no stored bytes — that keeps the PDF export and older clients working; the export requests photos with `crossOrigin="anonymous"` so the canvas stays untainted. **Accepted tradeoff:** a Cloudinary URL is publicly reachable by anyone who has it (the app itself still requires an approved login to *discover* it). The public_id is random and unguessable; switching to signed private delivery would mean signing every photo URL per request and giving up plain CDN caching.
- **Offline-tolerant auth gate.** The whole UI sits behind an auth check (GET `/api/auth/user`), which fails on a cold **offline** boot — so without special handling a user opening the app in the forest with no signal is stuck on the login screen and never reaches the camera. Fix (`src/lib/auth-context.tsx`): the last **approved** identity is cached in `localStorage`, and the gate serves it when the live check has no user AND (`navigator` is offline OR a revalidate is in flight). Rules that keep it safe: only approved users are ever cached (never a not-approved or signed-out account); online, the server's answer always wins; a live `user=null` while online = genuine sign-out → cache cleared; `user=null` while offline = network failure → cache kept. On the `online` event the auth hook's new `revalidate()` re-checks the server while the cached identity keeps serving, so the user isn't bounced to login mid-session and the queue drain resumes. localStorage is client-tamperable, so this only forges **offline UI** access on that one device — every API call is still enforced server-side by `requireApproved`. The auth hook itself is a plain local module (`src/lib/use-auth.ts`) since there is no external identity provider to redirect to any more: an expired session simply drops the cached identity and the login form reappears.
- **Category PDF export is client-side (jsPDF).** The Kategorien tab exports selected categories to a PDF entirely in the browser — no server route (`src/lib/pdf-export.ts`, wired from `src/pages/categories.tsx`); each plant's photo is loaded just-in-time from the same-origin `GET /plants/:id/image` endpoint (same-origin keeps the export canvas untainted). `jspdf` is dynamically `import()`-ed on click so it stays out of the main bundle. - **Photos are downscaled at capture, not stored full-resolution.** `scan.tsx` runs each selected photo through `downscaleFile` (`src/lib/image.ts` — decodes via an object URL instead of a base64 `FileReader` round-trip, cutting peak capture memory roughly in half, which is what used to trigger mid-scan tab reloads on low-memory phones; offscreen-canvas resize; defaults **1280px max edge / JPEG q0.72**, ~100–180 KB per photo; call sites pass no explicit numbers so the defaults are the single source of truth; formats the browser can't decode fall back to the original bytes instead of failing the capture) before queuing it — the queue drain then sends the already-downscaled photo to Gemini. `downscaleDataUrl` remains for photos stored in the queue before downscaling existed. **Why:** raw camera photos are several MB, which wastes storage and upload time, and — historically, when lists still embedded base64 images — exceeded mobile image-decode budgets and rendered thumbnails **blank** (not reproducible on desktop). 1280px stays crisp in the detail view and is ample for plant ID. A 1×1 placeholder image (data URL ~100 chars) can only come from a programmatic insert, never the camera/gallery UI — such rows are leftover test fixtures. ## Futterplaner (Tiere)

Plan and steps in `docs/futterplaner.md`. Fixed rules, no AI (`lib/feedCatalog.ts`, `lib/feedNeeds.ts`, `lib/feedPlanner.ts`, `routes/feed.ts`; tables `farm_feeds`, `feed_rations`; page `/farm/futter`).
- **Everything is on dry matter.** Catalogue values are per kg DM; own feeds are entered as printed on the label ("wie gefüttert", Ca/P in %) and converted with the dry matter (default 88 %) on save. Bedarf per species and life stage is for a typical animal (`weightKg`); the check shows an Ampel per nutrient (amount 0.9–1.3× intake, protein, fibre, Ca, P, copper for sheep) with fixed tips. Values are Richtwerte – to be checked by a specialist before the public start.
- **One ration per animal or herd** (partial unique indexes); a herd ration is per animal, group totals use the active members. Cats and dogs get no ration check.
- **Warnings cannot be dismissed**: plants the archive marks toxic for the species, mineral feed made for another species and copper over the limit (sheep), running withdrawal periods from the medical records. No kitchen scraps are suggested (VO (EG) 1069/2009 notice on the page).
- A feed in use cannot be deleted (409).
- **Fütterungsplan** (`lib/feedSeason.ts`, pure rules): a ration is `all`, `summer` (Apr–Oct) or `winter` (Nov–Mar), unique per target and season; the season's ration wins over the all-year one (`active`). A changed set of feeds on the ration in effect stores `previous_items`/`change_started_on`/`change_days` and the evaluation returns today's mixture (`transition`, four 25 % steps, 7/10/14 days by species); the switch to the next season's ration is computed, not stored, and ends the day before 1 April / 1 November. "Erinnern" makes daily "Füttern" stall tasks (07:00/12:00/18:00) whose notes start with "Futterplaner"; saving a ration and opening the plan refresh those notes (never switching a paused reminder back on). "Today" is `berlinDay()` – the integration test mocks it.
- **Vorrat & Kosten** (`lib/feedStock.ts`, `/farm/futter/vorrat`, table `feed_stocks`, one row per farm and feed): the row is the amount counted or bought on `counted_on`; what is left today is derived from the daily use of the rations in effect (not stored), a purchase adds to that and resets the day. `stockOverview()` is pure (stock status, costs per animal and month from `price_per_kg`, winter need 1 Nov–31 Mar from the winter rations). `winterGardenNeed()` hands Möhren/Futterrüben/Kürbis to `planGarden(…, rationWinter)`, which then replaces its winter rule of thumb (`fodder.winterFromRations`). `sendFeedDigests()` (from the push cron, 07:30, `feed_digest_log` claims farm and day like the garden digest) pushes "Futter nachkaufen" on a feed's reorder day and the day before it runs out.
- **Tipps & Rezepte** (`lib/feedRecipes.ts`, `lib/feedCalendar.ts`, `/farm/futter/tipps`, table `feed_recipes`): built-in recipes live in the code (`b:<key>`), sent-in ones in the table (`u:<id>`, status pending/approved/rejected) and are visible to others only after the app owner approves them (`/admin/feed-recipes`, card in Mehr); `recipeFlags()` marks scraps and poisonous ingredients for the owner, it does not block. The fodder calendar uses the garden catalog's harvest months, `FODDER_CROPS` of the Garten-Assistent and this season's `bed_plantings`.
- **Etikett per KI** (`lib/feedLabel.ts`, `POST /farms/:id/feeds/label`, farm AI limit): the model reads the label, the answer is coerced (implausible numbers → null, moisture → dry matter) and **nothing is saved** – the values fill the own-feed form and the user confirms them. Additives are stored with the feed (`farm_feeds.additives`); ionophore coccidiostats (Monensin, Salinomycin, …) give an `ionophore` warning for every species except poultry.

## Wetter für den Hof

Plan in `docs/wetter.md` (`lib/farmWeather.ts`, `routes/farm-weather.ts`, card `components/farm-weather-card.tsx`; columns `farms.postal_code/latitude/longitude`, table `weather_digest_log`).
- Location: the farm's own (admin sets postal code or GPS, rounded to 0.1°), else the first bed with one. Forecast: Bright Sky (DWD), three Berlin days from hourly records, cached an hour per rounded position; an unreachable service gives no days, never an error.
- `weatherWarnings()` is pure: frost/hard frost/heat/storm/heavy rain by the species on the farm (no animals → none), plus a watering hint when beds are planted this season.
- `sendWeatherDigests()` (push cron, 07:30) claims farm and day in `weather_digest_log` with the warning kinds and pushes only kinds that did not go out the day before; farms with nothing to warn about are claimed with `[]` so the cron does not ask again; a failed forecast is retried on the next call.
- Official DWD warnings: `officialAlerts()`/`pickAlerts()` (Bright Sky `/alerts`, cached 10 min per rounded position; actual met/health warnings, no all-clear, not expired, worst first) → `alerts`/`alertArea` in the weather answer. `sendAlertPushes()` runs on every cron call: severe/extreme only, farms with animals or beds; `weather_alert_log` keyed by event code + first day (DWD re-issues updates under new ids) and re-pushed only when the level rises.

## Arzneimittel-Vorrat

`lib/medicines.ts`, routes in `routes/farm-health.ts`, page `/farm/arzneimittel`; table `medicines`, columns `medical_records.medicine_id/dose/batch`, table `farm_push_log` (generic once-a-day push per farm and topic).
- A medicine holds amount and unit, batch, expiry and withdrawal periods for meat, milk and eggs. Used up or thrown away → archived (`archivedAt`); deleting is refused (409) once a health record used it.
- A health record may pick a medicine: the dose is required and comes off the stock (`adjustStock`, never below 0); an empty medication name and withdrawal period are filled from the medicine – the withdrawal for the animal's species is the longest of what it gives (`withdrawalFor`: poultry eggs/meat, ruminants milk/meat). A new use of an archived medicine, or one expired on the treatment date, is refused. Editing books the old dose back and the new one out; deleting a record gives its dose back. Records return `doseUnit` (joined from the medicine), the vet export has a column "Menge, Charge".
- `sendMedicineDigests()` (push cron, 07:30): 30 days before and on the expiry day, once per farm and day (`farm_push_log`, topic `medicines`).

## Saatgut

Details in `docs/saatgut.md` (`lib/seeds.ts`, `routes/farm-seeds.ts`, page `/beete/saatgut`; table `seeds`).

## Product

## Gotchas

- If `POST /api/plants/scan` returns 502 with "AI-Identifizierung fehlgeschlagen", check the API server logs first — this error is deliberately generic to the client, but the real cause (model 404, quota exceeded, truncated JSON) is logged server-side.
- Always run `pnpm --filter @workspace/db run push` after changing `lib/db/src/schema/plants.ts`, and restart the `api-server` workflow afterward.
- Always run `pnpm --filter @workspace/api-spec run codegen` after changing `lib/api-spec/openapi.yaml` — the server imports the generated zod schemas, so routes referencing new endpoints won't compile until codegen runs.
- The production deployment uses its **own database** (read-only from the workspace via SQL tools). Schema changes reach production automatically on publish; production *data* fixes (photo recompression, field backfills) must go through the password-gated `PATCH /api/plants/:id` endpoint of the **published** app.
- The API server refuses to start without a valid `JWT_SECRET` (≥16 chars) — that is deliberate: booting without it would silently accept nobody, or worse, sign tokens with a guessable key.
- A photo that shows up nowhere after a scan usually means `CLOUDINARY_URL` is missing or malformed — the scan itself still succeeds, the upload is skipped, and the reason is logged server-side.
- Deleting plants requires the `DELETE_PASSWORD` secret (the delete PIN). If it is unset, every delete returns 503 "Löschen ist derzeit nicht konfiguriert." — set it via Secrets (and make sure it is present in the deployment); it is never hardcoded.
