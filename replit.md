# Pflanzenscanner

Eine mobile-first, deutschsprachige Web-App, mit der Nutzer wilde Pflanzen per Foto scannen, per KI bestimmen lassen und in einem kategorisierten Archiv (Giftige Pflanzen, Essbare Pflanzen, Heilkräuter, Giftige Pilze, Essbare Pilze, Bäume, Sträucher, Moose) sammeln können.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server
- `pnpm --filter @workspace/pflanzenscanner run dev` — run the frontend
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/api-server run migrate:images` — one-off: move photos still stored in Replit Object Storage over to Cloudinary (must run on Replit; `--download-only` just backs them up locally)
- Required env: `DATABASE_URL` — Postgres connection string
- Required secret: `GEMINI_API_KEY` — user-provided Gemini API key (direct Generative Language API, not the Replit AI Integrations proxy)
- Required secret: `JWT_SECRET` — signing key for the login cookie (≥16 characters, any long random string). Changing it logs everyone out.
- Required secret: `CLOUDINARY_URL` — `cloudinary://<api_key>:<api_secret>@<cloud_name>` from the Cloudinary dashboard; all scan photos are uploaded there
- Required secret: `CRON_SECRET` — Bearer token for the cron endpoint (see "Push-Benachrichtigungen (Cron)" below)
- Optional secret: `REGISTRATION_CODE` — when set, `POST /auth/register` additionally requires this invitation code, and "Mit Google anmelden" only works for addresses that already have an account
- Optional secrets: `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — OAuth client (type "Webanwendung") from the Google Cloud console. Only when **both** are set does the login screen offer "Mit Google anmelden". Registered redirect URI: `<origin>/api/auth/google/callback`
- Optional env: `PUBLIC_BASE_URL` — canonical public origin (e.g. `https://kraeuter-hexe.onrender.com`). Used to build the Google callback URL instead of trusting proxy headers; set it wherever Google sign-in is used
- Optional env: `CLOUDINARY_FOLDER` — folder for uploads (default `kraeuterhexe`)

## Push-Benachrichtigungen (Cron)

Push-Erinnerungen werden nicht mehr durch einen `setInterval` im Server-Prozess ausgelöst, sondern durch einen externen Cron-Dienst. Das ist nötig damit Erinnerungen auch nach einem Scale-to-Zero (Autoscale mit 0 Mindest-Instanzen) zuverlässig ankommen.

**Einrichtung (einmalig, nach dem Deployment):**

1. Öffne [cron-job.org](https://cron-job.org) (kostenlos) und lege einen neuen Cronjob an.
2. **URL:** `https://<deine-deployed-domain>/api/cron/trigger-notifications`
3. **Methode:** `POST`
4. **Header:** `Authorization: Bearer <CRON_SECRET>`
5. **Intervall:** jede Minute (damit keine Erinnerungsminute übersprungen wird)
6. Den Wert von `CRON_SECRET` findest du in den Replit Secrets dieses Projekts.

**Lokal testen:**
```bash
curl -X POST https://<deine-deployed-domain>/api/cron/trigger-notifications \
  -H "Authorization: Bearer <CRON_SECRET>"
# → {"triggered": 0}   (0 wenn gerade kein Reminder fällig ist)
```

Die Funktion ist idempotent: mehrere Aufrufe innerhalb derselben Minute senden maximal eine Benachrichtigung pro Aufgabe/Guide pro Tag.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM (native pg enums for category/status fields)
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)
- Frontend: React + Vite, Outfit + Playfair Display fonts, earthy/forest-green nature palette
- AI vision: Google Gemini (`@google/genai`, primary model `gemini-flash-lite-latest` with `gemini-flash-latest` fallback + retry), called directly with the user's own API key

## Where things live

- `lib/db/src/schema/plants.ts` — `plantsTable` schema, `PLANT_CATEGORIES` / `HUMAN_STATUSES` / `POULTRY_STATUSES` enums (source of truth for valid values)
- `lib/api-spec/openapi.yaml` — API contract for `/plants/*` endpoints
- `artifacts/api-server/src/routes/plants.ts` — scan/list/get/delete/category-summary endpoints, plus `GET /plants/:id/image` and `GET /plants/:id/image/side` (binary photo delivery) and password-gated `PATCH /plants/:id` (maintenance updates)
- `artifacts/api-server/src/lib/plantIdentification.ts` — Gemini prompt, response parsing/coercion, deterministic category override logic
- `artifacts/api-server/src/lib/geminiClient.ts` — Gemini client construction from `GEMINI_API_KEY`
- `artifacts/pflanzenscanner/` — frontend (Scan, Archiv, Kategorien, Pflanze-Detail pages)

## Architecture decisions

- **Direct Gemini API key instead of Replit AI Integrations.** Both the managed OpenAI and Anthropic integrations were blocked by an account-upgrade requirement, and the user declined to upgrade or provide their own OpenAI/Anthropic key. The user instead provided their own `GEMINI_API_KEY` (via the secure secrets flow), so the backend calls the Gemini Generative Language API directly with `@google/genai` rather than going through the Replit AI proxy. Revisit if a managed integration becomes available.
- **Model choice is driven by IMAGE-request reliability, not text.** This app sends photos, and multimodal availability differs sharply from text on this key: `gemini-3.5-flash` and `gemini-flash-latest` answer text fine but return 503 "high demand" for nearly every image request, while `gemini-flash-lite-latest` reliably handles image requests (verified 4/4). So the primary model is `gemini-flash-lite-latest`, with `gemini-flash-latest` as fallback, and transient 503/429s are retried with backoff (see `requestPlantJson` in `plantIdentification.ts`). Always validate a model against a real image request, not a text smoke test. Older versioned IDs (`gemini-2.5-flash`/`gemini-2.0-flash`/`gemini-2.5-flash-lite`) return 404 "no longer available".
- **`thinkingConfig.thinkingBudget: 0` is required.** Without it, Gemini flash models silently consume part of `maxOutputTokens` on internal "thinking" tokens, truncating the JSON response before it's complete — this looked like a generic "invalid JSON" parse failure, not a token-budget issue. JSON is also parsed defensively (fences stripped, outermost `{...}` extracted) in case the model wraps or pads the output.
- **Category/status fields use native Postgres enums**, not free text, so invalid values can never be persisted regardless of code path — critical since these drive the safety badges.
- **Deterministic category override**: if the model says a plant is poisonous for humans, the archive `category` is forced to `poisonous` (unless the model picked a form-based bucket — `mushroom`, `tree`, `shrub`, `moss` — those always keep their own category; safety stays visible via the status badges), rather than trusting the model's own category pick — keeps archive grouping safety-consistent even if the model's `category` and `humanStatus` fields disagree.
- **Safety-first fallback**: any missing/unparseable `humanStatus` or `poultryStatus` defaults to `poisonous`, never to a "safe" value.
- **Duplicate scans are de-duplicated by botanical name.** `POST /plants/scan` matches the identified botanical (Latin) name case-insensitively against the archive; on a match it returns the existing entry with `alreadyInArchive: true` and creates no new row. The scan UI then points the user to the existing entry instead of navigating to a freshly created one.
- **Deleting an archived plant is password-gated server-side.** `DELETE /plants/:id` requires a `password` in the request body, verified against the `DELETE_PASSWORD` env var (stored as a Replit Secret, never hardcoded). It fails closed: if `DELETE_PASSWORD` is unset the endpoint returns 503 and deletes nothing. The password travels in the request body (not the URL/query) so it is never written to request logs.
- **Plant photos are served as binary images, never embedded in JSON.** All JSON responses (list, detail, scan result) exclude `image_data`; photos come from `GET /plants/:id/image`, which decodes the stored data URL and serves real image bytes with `ETag` + `Cache-Control: public, max-age=86400` (304 revalidation) and `X-Content-Type-Options: nosniff` behind an image-MIME allowlist (unknown stored MIME → `application/octet-stream`, so a hostile stored payload can never run as same-origin HTML; scan ingestion also rejects non-image data URLs). **Why:** embedding base64 photos made list payloads scale with total image bytes — production once reached ~69 MB for 13 plants, which mobile browsers simply cannot load. As a bonus the browser now caches photos independently of data. The category summary counts in SQL (`count(*) … group by`) instead of loading full rows.
- **Pilze are shown split into "Giftige Pilze" / "Essbare Pilze" — view categories, not data categories.** The DB/API keep the single `mushroom` category; the UI derives the two sub-groups from the required `humanStatus` enum. `src/lib/view-categories.ts` is the single source of truth for view-category order, labels, and mapping, used by both the Kategorien page and the PDF export. The summary endpoint returns per-humanStatus counts (`poisonousCount`/`edibleCount`) so the overview still needs no row loads. **Why a derived split:** zero migration — it applies automatically to already-scanned mushrooms, including those in the separate (workspace-read-only) production database; both mushroom views share one cached `category=mushroom` list query and are narrowed client-side.
- **Mushroom edibility requires a verified two-photo scan.** The scan page has a dedicated "Pilz scannen (2 Fotos)" flow: Bild 1 von oben (persisted as an IndexedDB draft — `mushroomDraft` store, DB v2 — so the camera-reload on low-memory phones can't lose it), then Bild 2 von der Seite; both photos are enqueued as ONE queue item, sent to Gemini as one labeled request, and stored on the entry (`image_data_side`, served via `GET /plants/:id/image/side`, shown on the detail page; `hasSideImage` in every plant response). A mushroom is listed as "essbar" ONLY when the side view exists AND the model set `mushroomEdibleConfident=true` (zweifelsfreie Art, eindeutig essbar, keine Verwechslungsgefahr mit giftigen Doppelgängern; missing flag = false). Enforcement is layered: `identifyPlant` downgrades to `poisonous` + German warning prefix in `edibilityDetails` at write time, and the shared `plantSelection` applies the same rule as a SQL CASE at read time (also in the category-summary counts) — so legacy single-photo mushrooms and maintenance PATCHes can never surface an unverified "essbarer Pilz". Stored rows are deliberately not mutated by the read gate; rescanning such an entry with the Pilz-Scan upgrades it in place via the botanical-name dedup (only when the existing row lacks a side image — a later 1-photo scan can never downgrade a verified entry).
- **Password-gated maintenance endpoint `PATCH /plants/:id`** (body: `password` + optional `imageData`/`habitat`/`siteConditions`/`otherUses`/`fertilizerTips`/`category`; strict field allowlist; `imageData` must be a JPEG/PNG/WebP data URL). **Why it exists:** the production deployment has its **own separate database** that is read-only from the workspace, so recompressing photos or backfilling new fact-sheet fields on already-scanned production plants can only happen through the deployed app itself. Both delete and patch verify the password by comparing sha256 digests with `timingSafeEqual` (constant-time).
- **Persist-first scan queue.** Every captured photo — online or offline — is stored locally in **IndexedDB** first (not localStorage, since photos are large data URLs) and then scanned from the queue; when online the drain starts immediately. **Why persist-first:** low-memory phones reload the tab seconds after the camera closes, killing an in-flight direct scan request and losing the photo — with the queue the photo survives the reload, is rescanned automatically on the next load, and the scan page still shows the result preview (server-side botanical-name dedup keeps crash-rescans duplicate-free). The drain reports each outcome as a `ScanResult` carrying the queue item id, so the scan page matches results to the exact photo it is waiting on (older backlog results can't mask the current photo's failure); a single new plant navigates to its detail page, several results render as a batch preview list. The queue lives in a React context (`src/lib/scan-queue-context.tsx`) over a thin IndexedDB wrapper (`src/lib/scan-queue.ts`); the "Warteschlange" page (`src/pages/pending.tsx`) lists waiting/failed items with retry/remove. Invariants that keep it safe: (1) **the transient "scanning" state is never persisted** — only `pending`/`error` are written, so a tab closed mid-scan leaves the item `pending` and it is retried on next load (nothing gets stuck); any legacy persisted `scanning` is normalized to `pending` on read, and the queue page re-reads storage on mount. (2) The drain is **single-flight** (a synchronous `processingRef` lock) and re-reads storage each iteration, so overlapping triggers can't double-process and a removed item can't be resurrected (the error-write is an atomic get+put in one IndexedDB transaction). (3) Network vs. server failures are told apart by `isNetworkError` (duck-typing the generated client's `err.name`): a network drop reverts the item to `pending` and stops the drain; a server error marks it `error` for manual retry.
- **Background sync is foreground-only (accepted limitation).** Draining happens only while the app is open: on the `online` event, on load when online, via a 30s safety-net interval, and via the manual "Jetzt scannen" button. True OS-level Background Sync is deliberately not implemented (unreliable, and unsupported on iOS), so queued photos scan when the user next opens the app with a connection — not while it is fully closed. Offline *capture* itself also depends on the installed PWA's cached app shell, which exists in production but not on the dev server (so a fully-offline relaunch can only be verified on the deployed PWA).
- **Sign-in is platform-independent: email + password, scrypt hashes, JWT cookie.** The app previously used Replit Auth (OIDC), which is bound to the Replit account that owns the repl and cannot follow the app to another host. It is replaced by `POST /auth/register` / `POST /auth/login` against the existing `users` table (`password_hash` column added; ids, `approved` and leaf counts untouched, so every existing account and all its data survive). Passwords are hashed with node's built-in **scrypt** (`src/lib/password.ts`, format `scrypt$N$r$p$salt$hash`, constant-time compare) — no native dependency to build on the new host. The session is a **JWT** (HS256, `jose`, 30-day TTL, `src/lib/token.ts`) in an HttpOnly/SameSite=Lax cookie named `auth`, re-issued at most once a day so long-lived logins roll forward. **Why no session table:** the middleware re-reads the user row on every request, so revoking approval or deleting an account takes effect immediately even though the token itself is stateless; the legacy `sessions` table is kept but unused. Registering with an email that already exists but has **no** password *claims* that row — that is how the pre-existing family accounts set their first password. That path inherits the row's `approved`/`isOwner` flags, so it is **refused unless `REGISTRATION_CODE` is set**: without it, guessing a family member's address would be enough to take over their (or the owner's) account. Registering a brand-new address without a code stays allowed — such an account starts unapproved and can do nothing until the owner lets it in. Login failures are rate-limited in memory (10 per 15 min per IP+email) and always answer with the same generic German message, so the endpoint reveals nothing about which emails exist.
- **"Mit Google anmelden" is an optional second door, not a dependency.** `GET /api/auth/google` → Google → `GET /api/auth/google/callback` (authorization code flow with PKCE, `src/routes/google-auth.ts`). It ends in exactly the same `auth` cookie as a password login, so nothing downstream knows the difference, and with `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` unset the routes are inert and the button is hidden (`GET /api/auth/providers`). An account is only matched or created from an address Google reports as **verified**; existing rows keep their `approved`/`isOwner` flags and only get missing name/photo filled in. When `REGISTRATION_CODE` is set an unknown address is turned away rather than creating a row — a redirect has nowhere to type the invitation code. The in-flight state lives in a signed, HttpOnly `__Host-` cookie (HMAC with `JWT_SECRET`): an unsigned one could be planted by an attacker to make somebody finish the sign-in as *their* Google account. Everything that can go wrong returns to the app as `?anmeldung=<code>`, which the login screen turns into German text.
- **Photos live on Cloudinary, not in the database or a Replit bucket.** Scan photos are uploaded to Cloudinary (`src/lib/imageStorage.ts`) and only the resulting public `https://res.cloudinary.com/...` URL is stored in `image_url` / `image_url_side`. **Why:** Replit Object Storage authenticates through a sidecar on localhost, so it silently stops working off-platform, and storing base64 in Postgres was what made list payloads explode in the first place. Uploads are **non-fatal**: a failing or unconfigured Cloudinary leaves the scan intact (the photo still lives in the device's IndexedDB and is retried by the image-backup endpoint). The SDK is imported lazily and the credential is parsed by us first (a pasted `CLOUDINARY_URL=cloudinary://…` line is tolerated) — otherwise a mistyped credential would crash the whole server at boot, because the SDK validates the env var at import time. Rows still holding a legacy `/objects/...` path are ignored by the client and converted by `migrate:images`. `GET /plants/:id/image` (and the insect/side variants) stay in place but now **302-redirect** to the CDN when the row has no stored bytes — that keeps the PDF export and older clients working; the export requests photos with `crossOrigin="anonymous"` so the canvas stays untainted. **Accepted tradeoff:** a Cloudinary URL is publicly reachable by anyone who has it (the app itself still requires an approved login to *discover* it). The public_id is random and unguessable; switching to signed private delivery would mean signing every photo URL per request and giving up plain CDN caching.
- **Offline-tolerant auth gate.** The whole UI sits behind an auth check (GET `/api/auth/user`), which fails on a cold **offline** boot — so without special handling a user opening the app in the forest with no signal is stuck on the login screen and never reaches the camera. Fix (`src/lib/auth-context.tsx`): the last **approved** identity is cached in `localStorage`, and the gate serves it when the live check has no user AND (`navigator` is offline OR a revalidate is in flight). Rules that keep it safe: only approved users are ever cached (never a not-approved or signed-out account); online, the server's answer always wins; a live `user=null` while online = genuine sign-out → cache cleared; `user=null` while offline = network failure → cache kept. On the `online` event the auth hook's new `revalidate()` re-checks the server while the cached identity keeps serving, so the user isn't bounced to login mid-session and the queue drain resumes. localStorage is client-tamperable, so this only forges **offline UI** access on that one device — every API call is still enforced server-side by `requireApproved`. The auth hook itself is a plain local module (`src/lib/use-auth.ts`) since there is no external identity provider to redirect to any more: an expired session simply drops the cached identity and the login form reappears.
- **Category PDF export is client-side (jsPDF).** The Kategorien tab exports selected categories to a PDF entirely in the browser — no server route (`src/lib/pdf-export.ts`, wired from `src/pages/categories.tsx`); each plant's photo is loaded just-in-time from the same-origin `GET /plants/:id/image` endpoint (same-origin keeps the export canvas untainted). `jspdf` is dynamically `import()`-ed on click so it stays out of the main bundle. The document mirrors the app: categories in the fixed view-category order (giftig → essbar → Heilkräuter → giftige/essbare Pilze → Bäume → Sträucher → Moose), each on its own page under a colored band, newest-first within a category, each plant showing its image + German/botanical name + scan date + the two safety badges + the full fact-sheet sections. Three deliberate choices keep it fast and safe on phones: (1) images are downscaled and re-encoded to JPEG on an offscreen canvas before embedding (source photos are multi-MB data URLs); (2) the document is planned from the lightweight `getCategorySummary` counts and each category's plants are fetched **just-in-time** during the render loop so all image payloads are never held in memory at once; (3) export is guarded against concurrent re-entry by a `useRef` lock (not just the disabled button). jsPDF's core `helvetica` renders German umlauts correctly, so no custom font is embedded.
- **Photos are downscaled at capture, not stored full-resolution.** `scan.tsx` runs each selected photo through `downscaleFile` (`src/lib/image.ts` — decodes via an object URL instead of a base64 `FileReader` round-trip, cutting peak capture memory roughly in half, which is what used to trigger mid-scan tab reloads on low-memory phones; offscreen-canvas resize; defaults **1280px max edge / JPEG q0.72**, ~100–180 KB per photo; call sites pass no explicit numbers so the defaults are the single source of truth; formats the browser can't decode fall back to the original bytes instead of failing the capture) before queuing it — the queue drain then sends the already-downscaled photo to Gemini. `downscaleDataUrl` remains for photos stored in the queue before downscaling existed. **Why:** raw camera photos are several MB, which wastes storage and upload time, and — historically, when lists still embedded base64 images — exceeded mobile image-decode budgets and rendered thumbnails **blank** (not reproducible on desktop). 1280px stays crisp in the detail view and is ample for plant ID. A 1×1 placeholder image (data URL ~100 chars) can only come from a programmatic insert, never the camera/gallery UI — such rows are leftover test fixtures. Legacy oversized rows are recompressed in place through the maintenance PATCH endpoint (ImageMagick `-auto-orient -resize 1280x1280> -quality 72`).

## Installation (Android/PWA)

The frontend is set up as an installable Progressive Web App via `vite-plugin-pwa` (see `artifacts/pflanzenscanner/vite.config.ts`). On Android, opening the deployed URL in Chrome offers "Zum Startbildschirm hinzufügen" / an automatic install prompt — no Play Store package exists or is needed. Manifest icons live in `artifacts/pflanzenscanner/public/` (`icon-192.png`, `icon-512.png`, `maskable-icon-512.png`, generated from `icon.svg`/`maskable-icon.svg`). API calls are excluded from the service worker cache (`NetworkOnly`) so scan/archive data always stays fresh. A redeploy is required after this setup for the manifest/service worker to be live in production.

## Product

- **Scan**: take/upload a photo of a plant; Gemini vision returns German name, botanical name, category, and full fact sheet. For Pilze there is a dedicated "Pilz scannen (2 Fotos)" flow (Bild 1 von oben → Bild 2 von der Seite); only a confidently identified edible mushroom with both photos is ever listed as "essbar".
- **Pflanze-Detail**: shows two distinct, unmistakable color-coded badges directly under the plant name — "Status Mensch" (green/Essbar vs. red/GIFTIG) and "Status Geflügel" (green/Genießbar vs. red/GIFTIG für Geflügel) — plus explanations, active ingredients, habitat info ("Standort & Vorkommen" — where the plant usually grows; "Standortansprüche" — what the site must provide: light, soil, moisture, nutrients), and medicinal benefits for both humans and poultry. Two further sections: "Weitere Nutzung" (`otherUses` — practical uses beyond eating/medicine, e.g. kaliumhaltige Jauche/Sud from Beinwell or Brennnessel, mulch, dye) and "Düngung im Eigenanbau" (`fertilizerTips` — how to fertilize when growing the plant yourself). All text sections are hidden when empty (legacy rows before backfill) and appear identically in the PDF export.
- **Archiv**: chronological list of all past scans with quick-glance badges.
- **Kategorien**: counts and browsing by 8 view categories (Giftige Pflanzen, Essbare Pflanzen, Heilkräuter, Giftige Pilze, Essbare Pilze, Bäume, Sträucher, Moose). Each category can be checkbox-selected (or "Alle auswählen") and exported to a single, print-ready PDF via "Als PDF".

## Gotchas

- If `POST /api/plants/scan` returns 502 with "AI-Identifizierung fehlgeschlagen", check the API server logs first — this error is deliberately generic to the client, but the real cause (model 404, quota exceeded, truncated JSON) is logged server-side.
- Always run `pnpm --filter @workspace/db run push` after changing `lib/db/src/schema/plants.ts`, and restart the `api-server` workflow afterward.
- Always run `pnpm --filter @workspace/api-spec run codegen` after changing `lib/api-spec/openapi.yaml` — the server imports the generated zod schemas, so routes referencing new endpoints won't compile until codegen runs.
- The production deployment uses its **own database** (read-only from the workspace via SQL tools). Schema changes reach production automatically on publish; production *data* fixes (photo recompression, field backfills) must go through the password-gated `PATCH /api/plants/:id` endpoint of the **published** app.
- The API server refuses to start without a valid `JWT_SECRET` (≥16 chars) — that is deliberate: booting without it would silently accept nobody, or worse, sign tokens with a guessable key.
- A photo that shows up nowhere after a scan usually means `CLOUDINARY_URL` is missing or malformed — the scan itself still succeeds, the upload is skipped, and the reason is logged server-side.
- Deleting plants requires the `DELETE_PASSWORD` secret (the delete PIN). If it is unset, every delete returns 503 "Löschen ist derzeit nicht konfiguriert." — set it via Secrets (and make sure it is present in the deployment); it is never hardcoded.
