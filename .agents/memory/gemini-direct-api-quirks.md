---
name: Gemini direct API quirks
description: Non-obvious failure modes when calling the Gemini Generative Language API directly (not via a managed proxy) with a user-supplied API key.
---

- Model availability varies by key/tier, drifts over time, AND differs by modality. Critically: a model can answer TEXT requests fine but be capacity-blocked (503 "high demand"/UNAVAILABLE) for IMAGE requests on the very same key. Observed on one real-world key: `gemini-3.5-flash` and `gemini-flash-latest` returned 503 for nearly every image request while succeeding on text-only calls; `gemini-flash-lite-latest` reliably handled the image workload (4/4). Older versioned IDs (`gemini-2.5-flash`, `gemini-2.0-flash`, `gemini-2.5-flash-lite`) return 404 "no longer available". Lesson: validate a model with the ACTUAL workload (send a real image if your app sends images) — a text smoke test is misleading — and prefer a fallback chain of models + transient-503/429 retry with backoff over betting on a single model.
- Gemini 2.x models can silently consume part of `maxOutputTokens` on internal "thinking" tokens even when you only want a final JSON answer. This truncates the response mid-JSON, which surfaces as a generic "invalid JSON" parse error with no indication it was a token-budget issue. The fix (`thinkingConfig: { thinkingBudget: 0 }`) ONLY works on thinking-capable models (gemini-2.5-flash/pro). Passing it to non-thinking models (gemini-flash-lite-latest, gemini-flash-latest) causes INVALID_ARGUMENT (400) on every image request — omit thinkingConfig entirely for those models.
- Free-tier keys can have a request quota of 0 for a given model until billing is enabled on the linked Google account — this shows up as a 429 RESOURCE_EXHAUSTED, not an auth error, even though the key itself is valid and authenticates fine.
